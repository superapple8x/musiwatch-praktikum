Cara ukur (penting, lihat `docs/p1_prosedur.md`):

- Permintaan memakai `Accept-Encoding: identity` agar body 13.358 bita benar-benar

  nyaris tidak terasa.
- Angka diambil pada **koneksi yang sudah hangat** (permintaan kedua dari satu klien).
  Koneksi TCP baru ke `10.0.2.2` selalu memakan ~503 ms apa pun profilnya (artifact

- Profil dijalankan oleh `scripts/throttle_proxy.py` (port 9000), karena
  `-netdelay`/`-netspeed` emulator tidak diterapkan pada lalu lintas data (Langkah 3).

Kesimpulan (dengan angka):

- **edge 473 ms = 158x full (3 ms)**; **hsdpa 129 ms = 43x full**. Urutan sesuai teori.
- Model `total = latensi + transfer` cocok: edge 240 ms + 13.358 B / 473,6 kbit/s

- Pada edge, transfer 226 ms hampir separuh total (48 %), sedangkan pada hsdpa transfer

## 3. (P1.2) Kontrak API klien

Endpoint (`api/app/main.py`):

| Endpoint | Parameter | Balasan |
| --- | --- | --- |
| `GET /v1/stations` | `limit` (default 50, dijepit 1..500), `offset` (default 0) | `200 {"items":[...], "next_offset": int\|null}` |
| `GET /v1/flaky` | - | 30 % `503`; sisanya tidur 50-400 ms lalu `200 {"ok":true,"ts":...}` |

Paginasi: 500 stasiun, `limit=50` -> 10 halaman; berhenti saat `next_offset` bernilai
`null` (bukan saat `items` kosong). Klien memakai `next_offset` sebagai `offset`
berikutnya, tidak menebak dari jumlah item.

ETag: header `ETag: "<16 hex>"` (sha256 halaman) + `Cache-Control: max-age=60`. Klien
mengirim `If-None-Match`; bila cocok server membalas `304` tanpa body, dan klien memakai
salinan yang sudah ada (tidak mengunduh ulang).

Tabel status code -> reaksi aplikasi:

| Status | Arti | Reaksi aplikasi |
| --- | --- | --- |
| 200 | sukses | parse `items`, lanjut selama `next_offset != null` |
| 304 | tidak berubah | pakai cache, tidak ada body; dihitung sukses |
| 400 | parameter salah (mis. `limit=0` dijepit, `offset` negatif) | tampilkan kesalahan, **jangan** retry |
| 404 | path salah | perbaiki kode, jangan retry |
| 405 | metode salah (contoh nyata: `curl -sI` mengirim HEAD) | perbaiki kode, jangan retry |
| 429 | terlalu banyak permintaan | retry dengan backoff (masuk daftar `retryable`) |
| 500 | kesalahan server | **tidak** di-retry oleh interceptor modul (daftar hanya 429/502/503/504); tampilkan kesalahan |
| 502/503/504 | gateway/server tidak tersedia | retry dengan backoff |
| IOException / timeout | koneksi putus, read timeout 10 s | retry (ditangkap interceptor) |
| 3xx | redirect | diikuti otomatis oleh OkHttp untuk GET |

## 4. (P1.3) Bukti implementasi

`app/src/main/java/id/unsri/musiwatch/net/RetryInterceptor.kt` (verbatim modul):

```kotlin
class RetryInterceptor(private val maxRetries: Int = 3) : Interceptor {
    private val retryable = setOf(429, 502, 503, 504)
    override fun intercept(chain: Interceptor.Chain): Response {
        val request = chain.request()
        if (request.method !in setOf("GET", "PUT", "DELETE")) return chain.proceed(request)
        var attempt = 0
        while (true) {
            try {
                val response = chain.proceed(request)
                if (response.code !in retryable || attempt >= maxRetries) return response
                response.close()
            } catch (e: IOException) {
                if (attempt >= maxRetries) throw e
            }
            val backoffMs = (500L shl attempt) + Random.nextLong(0, 250)  // 0,5 s, 1 s, 2 s + jitter
            Thread.sleep(backoffMs)
            attempt++
        }
    }
}
```

Hasil 20 panggilan `GET /v1/flaky` dari aplikasi (satu klien, `docs/bukti/03_*`):

| Mode | Sukses | Gagal | Total | Rata-rata |
| --- | --- | --- | --- | --- |
| tanpa retry | 15/20 | 5 | 3.003 ms | 150 ms |
| dengan retry | 20/20 | 0 | 8.094 ms | 405 ms |

Kegagalan 503 acak 30 % membuat ~6 dari 20 gagal; terukur 5. Dengan retry, semua 20
sukses, tetapi total naik 2,7x (3,0 s -> 8,1 s) karena setiap kegagalan membayar backoff
0,5/1/2 s + jitter. Jadi retry menukar **keandalan** dengan **waktu**, bukan gratis.

Alasan POST tidak di-retry otomatis: POST **tidak idempoten**. Bila balasan hilang di
tengah jalan, klien tidak tahu apakah server sudah memproses; mengirim ulang bisa
membuat data ganda (mis. dua transaksi). Interceptor karena itu hanya mengulang
GET/PUT/DELETE, yang menurut HTTP aman diulang (PUT/DELETE idempoten). Kalau POST perlu
diulang, harus ada idempotency key di server.

Catatan implementasi (TAMBAHAN, di luar teks modul):

- `HttpClients.kt` ditambah varian `baseUrl` dan `Accept-Encoding: identity`, serta
  `EventListener` untuk memisahkan connect/kirim/terima/unduh.
- `MainViewModel` memakai satu `OkHttpClient` dan satu panggilan pemanasan. Sebelum ini
  setiap tap membuat klien baru, dan koneksi baru ke `10.0.2.2` selalu ~503 ms sehingga
  ketiga profil tampak sama (~502 ms). Bug pengukuran lain yang ditemukan: ekspresi
  `(elapsed) to (body.string())` menghitung `elapsed` **sebelum** body dibaca, jadi yang
  terukur hanya TTFB. Keduanya sudah diperbaiki.

## 5. Refleksi

Bila 1.000 klien me-retry tanpa jitter pada saat yang sama, kegagalan 30 % membuat ~300
klien menunggu tepat 0,5 s lalu menembak bersamaan; gelombang berikutnya ~90 klien pada
1 s, lalu ~27 pada 2 s. Karena tidak ada jitter, retry menjadi **sinkron**: beban datang
sebagai lonjakan 300 permintaan sekaligus, bukan tersebar. Server yang sedang kepayahan
menganggap lonjakan itu sebagai serangan, waktu antre naik, timeout bertambah, dan setiap
timeout memicu retry baru - **retry storm** dengan amplifikasi sampai 4x (1 percobaan +
3 retry) di atas beban awal. Dampaknya bukan hanya 503 yang berulang, tetapi antrean yang
makin panjang, latensi naik untuk klien yang tadinya sukses, dan kemungkinan cascading
failure ke layanan lain.

Peredamnya: (1) **full jitter** - tunggu `random(0, min(cap, base * 2^attempt))`, bukan
`500 ms shl attempt`; (2) batasi jumlah retry dan hormati `Retry-After`; (3) circuit
breaker agar klien berhenti mencoba saat server sudah jelas down; (4) idempotency key
untuk operasi non-idempoten; (5) rate limit/antrean di sisi server. Jitter menyebar 300
retry ke jendela 0-500 ms sehingga puncaknya turun ~2 orde besaran, dan backoff
eksponensial memberi server waktu pulih.
