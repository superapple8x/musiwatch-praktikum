Mengapa DATABASE_URL tidak ditanam di image?
1. Prinsip Image Immutability: Satu image Docker yang sama harus bisa digunakan di berbagai lingkungan (development, staging, dan production) hanya dengan mengubah environment variable saat container dijalankan, tanpa perlu melakukan build ulang image.
2. Keamanan Kredensial: Menanam URL database di dalam Dockerfile atau image akan mengekspos username dan password database ke riwayat layer Docker dan registry publik.

## 3. (P2.3) Perbandingan varian Dockerfile
| Varian | Ukuran image | Waktu build ulang setelah ubah 1 baris |
| --- | --- | --- |
| slim (Dockerfile) | 246 MB | 5.8 detik |
| full (variants/Dockerfile.full) | 1.67 GB | 2.2 detik (build awal 203.6 detik) |
| salin kode dulu (variants/Dockerfile.nocache) | 246 MB | 18.9 detik |

Penjelasan dengan konsep layer cache:
Docker mengeksekusi instruksi baris demi baris dan menyimpan hasilnya sebagai layer cache. Jika suatu layer berubah, maka layer tersebut dan seluruh layer berikutnya otomatis dianggap kedaluwarsa (cache invalidation) dan harus diproses ulang dari awal.
Pada varian slim standar (Dockerfile), file requirements.txt disalin terlebih dahulu dan dijalankan pip install sebelum menyalin kode aplikasi (COPY app/ ./app/). Saat satu baris komentar ditambahkan di main.py, layer instalasi pip tetap utuh di cache sehingga proses build ulang selesai dalam waktu singkat (5.8 detik).
Pada varian salin kode dulu (Dockerfile.nocache), instruksi COPY . . dijalankan sebelum pip install. Akibatnya, setiap perubahan satu baris kode membatalkan cache layer pip, memaksa Docker mengunduh dan memasang ulang seluruh dependensi dari awal (memakan waktu 18.9 detik).
Pada varian full, image menyertakan seluruh toolchain kompilator C dan perkakas OS yang tidak dibutuhkan pada tahap runtime aplikasi sehingga ukurannya membengkak hingga 1.67 GB.

## 4. (P2.3) Resource, pemulihan, dan limit memori
Hasil docker stats:
1. Saat idle:
deploy-api-1 memakai CPU 0.09% dan RAM 32.21 MiB / 256 MiB (12.58%).
deploy-db-1 memakai CPU 0.00% dan RAM 23.95 MiB / 7.677 GiB (0.30%).
2. Saat diberi 200 permintaan beruntun:
CPU deploy-api-1 meningkat sesaat untuk melayani koneksi paralel, sedangkan pemakaian RAM stabil di rentang 32-35 MiB.

Waktu pemulihan pod (Self-Healing):
Setelah ketiga pod dihapus secara paksa (kubectl delete pod -l app=musiwatch-api --wait=false), Kubernetes mendeteksi selisih desired state dan menjadwalkan 3 pod pengganti baru. Waktu dari perintah penghapusan hingga ketiga pod baru berstatus 1/1 Running dan siap melayani trafik adalah 11 detik.

Status dan pesan event saat limit memori 32Mi:
Status pod: CrashLoopBackOff.
Pesan event dari kubectl describe: Reason: OOMKilled, Exit Code: 137.
Penyebab: Proses runtime Python FastAPI membutuhkan memori baseline minimal sekitar 32-35 MiB saat startup. Ketika batas memori disetel ke 32 MiB, kernel Linux cgroups mendeteksi alokasi memori melampaui batas dan mematikan kontainer dengan sinyal SIGKILL (Exit Code 137).

Rekomendasi request/limit:
Nilai request memori disarankan minimal 64 MiB hingga 128 MiB (memberi headroom aman saat startup), dan limit memori disetel ke 256 MiB hingga 512 MiB untuk menampung lonjakan alokasi saat pemrosesan request tinggi. Untuk CPU, disarankan request 100m-250m dan limit 500m-1 CPU.

## 5. Refleksi
Mengapa probe liveness sengaja tidak memeriksa database?
Liveness probe bertujuan memeriksa apakah proses internal aplikasi masih berjalan normal atau mengalami deadlock/macet. Jika liveness probe dikonfigurasi untuk memeriksa koneksi database, maka saat database mengalami gangguan sementara (misalnya restart service, failover, atau pemeliharaan berkala selama 1 menit), seluruh pod API akan serentak gagal liveness probe.
Akibatnya, Kubernetes akan me-restart seluruh pod API secara bersamaan dan berulang kali (cascading restart loop / thundering herd problem). Me-restart pod API tidak akan menyelesaikan masalah database yang sedang down, justru akan memperparah beban server dan merusak ketersediaan sistem.
Pemeriksaan koneksi database harus diletakkan pada readiness probe. Jika database mati, readiness probe akan gagal dan Kubernetes hanya akan mencabut pod dari routing service (tidak mengirim trafik pengguna ke pod tersebut), tanpa membunuh proses aplikasinya. Begitu database pulih, pod otomatis kembali menerima trafik tanpa perlu me-reboot kontainer.
