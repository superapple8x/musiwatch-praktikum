## 1. P3.1 – Analisis Kebutuhan Data

Aplikasi MusiWatch membutuhkan mekanisme penyimpanan dan sinkronisasi data pengukuran kualitas air. Data yang disimpan meliputi ID pengukuran, ID stasiun, ID petugas, nilai pH, tingkat kekeruhan (turbidity), suhu, catatan, waktu pengukuran, versi data, penanda penghapusan, dan status sinkronisasi pada perangkat.

Data pengukuran dapat diperbaiki setelah dicatat. Karena itu, sistem perlu membedakan data baru, data yang diperbarui, dan data yang dihapus. Setiap pengukuran memiliki ID unik dan nomor versi agar perubahan dapat diperiksa ketika dikirim ke server.

Konflik dapat terjadi ketika dua perangkat mengubah data yang sama sebelum melakukan sinkronisasi. Contohnya, kedua perangkat membaca data versi 1. Perangkat pertama mengirim perubahan lebih dahulu sehingga versi di server menjadi 2. Ketika perangkat kedua mengirim perubahan dengan acuan versi 1, server menolak perubahan tersebut sebagai konflik karena versi dasarnya sudah tidak sesuai.

Pada perangkat Android, status sinkronisasi digunakan untuk membedakan data yang menunggu dikirim (`PENDING`), data yang sudah tersinkronisasi (`SYNCED`), dan data yang mengalami konflik (`CONFLICT`).

Penghapusan data menggunakan mekanisme tombstone. Data tidak langsung dihapus secara permanen, tetapi diberi penanda `deleted = true`. Dengan demikian, informasi penghapusan tetap dapat dikirim ke perangkat lain melalui proses sinkronisasi.

Sistem juga perlu memiliki penanda urutan perubahan yang konsisten. Waktu pada perangkat dapat berbeda karena pengaturan jam yang tidak sama. Oleh sebab itu, server menggunakan `change_seq` sebagai urutan perubahan yang dihasilkan di sisi server, bukan mengandalkan waktu perangkat sebagai cursor sinkronisasi.

## 2. P3.2 – Desain Sinkronisasi

### A. Struktur Data Lokal dan Server

Penyimpanan lokal Android menggunakan Room Database. Entitas pengukuran menyimpan identitas pengukuran, stasiun, petugas, nilai pengukuran, catatan, waktu pengukuran, versi, penanda penghapusan, dan status sinkronisasi.

Pada sisi server, PostgreSQL menggunakan tabel `measurements`. Kolom penting pada tabel tersebut adalah:

| Kolom | Keterangan |
|---|---|
| `id` | ID unik pengukuran |
| `station_id` | ID stasiun pengukuran |
| `officer_id` | ID petugas |
| `ph` | Nilai pH air |
| `turbidity_ntu` | Tingkat kekeruhan air |
| `temp_c` | Suhu air |
| `note` | Catatan pengukuran |
| `measured_at` | Waktu pengukuran |
| `version` | Nomor versi data |
| `deleted` | Penanda penghapusan |
| `change_seq` | Urutan perubahan dari server |

Kolom `version` digunakan untuk pemeriksaan perubahan data, sedangkan `change_seq` digunakan untuk mengambil perubahan secara bertahap. Struktur tabel dan sequence didefinisikan pada `api/db/001_init.sql`.

### B. Proses Push

Push merupakan proses pengiriman perubahan dari perangkat Android ke server. Endpoint yang digunakan adalah:

`POST /v1/sync/push`

Perangkat mengirim daftar perubahan melalui atribut `changes`. Setiap perubahan membawa identitas data dan informasi versi dasar (`base_version`). Server kemudian memeriksa apakah data merupakan data baru, pengiriman ulang, pembaruan yang valid, atau perubahan yang mengalami konflik.

Respons push dapat memiliki status berikut:

- `created`: data baru berhasil dibuat di server.
- `duplicate`: data dengan ID tersebut sudah pernah diterima.
- `updated`: perubahan berhasil diterapkan.
- `conflict`: perubahan ditolak karena versi dasar tidak sesuai dengan versi data di server.

Pemeriksaan versi diperlukan agar perubahan lama tidak langsung menimpa data yang lebih baru.

### C. Proses Pull

Pull merupakan proses pengambilan perubahan dari server ke perangkat. Endpoint yang digunakan adalah:

`GET /v1/sync/pull?since={cursor}`

Parameter `since` berisi cursor terakhir yang telah disimpan oleh perangkat. Server mengirim daftar perubahan setelah cursor tersebut, beserta `next_cursor` dan `has_more`.

Perangkat menggunakan `next_cursor` untuk melanjutkan proses pull pada sinkronisasi berikutnya. Dengan cara ini, perangkat tidak harus mengambil seluruh data dari awal setiap kali melakukan sinkronisasi.

### D. Penanganan Konflik

Konflik terjadi ketika nilai `base_version` dari perangkat tidak sama dengan versi data yang tersimpan di server. Server mengembalikan status `conflict`, kemudian Android mengubah status sinkronisasi data lokal menjadi `CONFLICT`.

Data yang mengalami konflik perlu ditinjau sebelum diselesaikan. Aplikasi sebaiknya menampilkan nilai lokal dan nilai server agar petugas dapat membandingkannya. Data lokal yang belum tersinkronisasi tidak seharusnya langsung ditimpa oleh data hasil pull.

### E. Penggunaan Cursor `change_seq`

`change_seq` digunakan sebagai penanda urutan perubahan yang dibuat oleh server. Penggunaan cursor dari server mengurangi ketergantungan pada jam perangkat yang mungkin tidak akurat atau berbeda satu sama lain.

Dengan cursor tersebut, perangkat dapat meminta perubahan secara bertahap dan melanjutkan sinkronisasi dari posisi terakhir yang telah diproses.

## 3. P3.3 – Implementasi dan Bukti Pengujian

### A. Implementasi Backend

Backend dibuat menggunakan FastAPI. Router sinkronisasi berada pada `api/app/sync.py` dengan prefix `/v1/sync`. Implementasi menyediakan endpoint push dan pull untuk pertukaran data antara perangkat Android dan server.

Skema database PostgreSQL disiapkan melalui `api/db/001_init.sql`. Database menyimpan data pengukuran, nomor versi, penanda penghapusan, dan urutan perubahan.

### B. Implementasi Android

Aplikasi Android menggunakan Room Database untuk penyimpanan lokal. Kode penyimpanan berada pada package `data`, sedangkan komunikasi jaringan dan sinkronisasi berada pada package `net` dan `sync`.

`MeasurementDao` menangani pembaruan status sinkronisasi dan penerapan perubahan dari server. Hasil push dengan status `created`, `updated`, atau `duplicate` ditandai sebagai `SYNCED`, sedangkan hasil `conflict` ditandai sebagai `CONFLICT`.

`SyncWorker` menjalankan proses push dan pull melalui WorkManager. Jika terjadi `IOException`, worker mengembalikan `Result.retry()` agar proses dapat dicoba kembali oleh WorkManager.

### C. Bukti Pengujian

### D. Penanganan Gangguan Jaringan

Pada implementasi Android, `SyncWorker` menangani kegagalan komunikasi dengan mengembalikan `Result.retry()` ketika terjadi `IOException`. Mekanisme ini memungkinkan WorkManager menjadwalkan percobaan ulang. Data yang belum berhasil dikirim tetap berada di penyimpanan lokal untuk diproses kembali.

Pengujian khusus menggunakan mode pesawat perlu didokumentasikan dengan bukti tersendiri apabila diminta dalam modul praktikum.

## 4. Refleksi

Mekanisme sinkronisasi diperlukan agar data pengukuran yang dibuat pada perangkat dapat diteruskan ke server dan diterima oleh perangkat lain. Penggunaan nomor versi membantu mencegah perubahan lama menimpa data terbaru. Sementara itu, cursor `change_seq` membantu perangkat mengambil perubahan secara bertahap.

Penanganan konflik menjadi bagian penting karena perubahan dari beberapa perangkat dapat terjadi pada waktu yang berdekatan. Data berstatus `CONFLICT` sebaiknya ditampilkan sebagai data yang perlu ditinjau. Petugas perlu dapat membandingkan data lokal dan data server sebelum menentukan perubahan yang akan dipertahankan.

Mekanisme tombstone juga diperlukan agar informasi penghapusan tetap tersampaikan ke seluruh perangkat. Dengan demikian, data yang sudah dihapus tidak muncul kembali hanya karena perangkat lain belum menerima informasi penghapusan tersebut.

## 5. Kesimpulan

Praktikum 3 menerapkan mekanisme backend dan sinkronisasi data pada aplikasi MusiWatch. Implementasi mencakup penyimpanan lokal menggunakan Room, backend FastAPI, database PostgreSQL, proses push dan pull, pemeriksaan versi, penanganan konflik, cursor perubahan, serta mekanisme tombstone.

Berdasarkan struktur kode dan berkas bukti yang tersedia, komponen utama implementasi telah disiapkan dalam proyek. Pengujian tambahan, terutama pengujian gangguan jaringan secara langsung, tetap perlu dilengkapi dengan bukti apabila menjadi persyaratan modul.
