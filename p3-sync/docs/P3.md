## 1. (P3.1) Analisis kebutuhan data

Stasiun adalah data referensi. Petugas membuat pengukuran secara offline dengan UUID baru. Pencatatan pengukuran baru bersifat append-only pada tahap input. Setelah dibuat, satu pengukuran masih dapat dikoreksi atau ditandai terhapus. Tabel `measurements` menyimpan keadaan terakhir per UUID. Jejak audit lengkap akan memerlukan tabel peristiwa append-only tersendiri.

Pembuatan ulang dengan UUID yang sama harus idempoten agar pengiriman ulang tidak menggandakan data. Dua petugas yang mengoreksi versi yang sama dapat bertabrakan. Server menerima perubahan pertama dan mengembalikan `conflict` untuk perubahan dengan versi lama. Room memberi konsistensi lokal segera setelah penyimpanan. Setelah jaringan pulih, klien dan server mencapai konsistensi eventual melalui push dan pull, dengan konflik tetap terlihat untuk ditinjau.

Jika transaksi A mendapat `change_seq` 10 dan transaksi B mendapat 11 lalu commit lebih dulu, pull dapat melihat 11 dan melewatkan A ketika meminta `since=11`. Backend mengambil `pg_advisory_xact_lock(42)` sebelum menulis satu batch. Penulis push berbagi lock itu sampai transaksi selesai, sehingga perubahan berikutnya tidak dapat commit mendahului perubahan sebelumnya. Lock tunggal ini memadai untuk skala praktikum dengan konsekuensi batch penulis diproses bergiliran.

## 2. (P3.2) Desain

| Lokasi | Skema dan peran |
| --- | --- |
| Room `measurements` | UUID teks sebagai PK, ID stasiun dan petugas, pH, kekeruhan, suhu, catatan, `measuredAt` dalam epoch milidetik, versi lokal nullable, `deleted`, dan `syncState` (`PENDING`, `SYNCED`, `CONFLICT`). |
| PostgreSQL `measurements` | UUID sebagai PK, ID stasiun dan petugas, kolom numerik pengukuran, catatan, `measured_at TIMESTAMPTZ`, `version` berawal dari 1, `deleted`, dan `change_seq BIGINT` berindeks. |
| Preferensi klien `sync` | Cursor terakhir disimpan setelah halaman pull berhasil diterapkan ke Room. |

`POST /v1/sync/push` menerima `{"changes":[...]}` dengan maksimum 500 item. Setiap item membawa UUID, `base_version`, ID stasiun dan petugas, nilai pengukuran, waktu pengukuran, dan `deleted`. Respons `{"results":[...]}` memuat ID dan status per item.

| Status | Makna |
| --- | --- |
| `created` | UUID baru tersimpan dengan `version=1`. |
| `duplicate` | UUID sudah ada dan `base_version=null`. Server mengembalikan versi yang ada. |
| `updated` | `base_version` cocok. Versi bertambah satu. `deleted=true` menghasilkan tombstone. |
| `conflict` | `base_version` sudah tertinggal. Server mempertahankan barisnya dan mengirim `server_version`. |

`GET /v1/sync/pull?since=<cursor>&limit=<jumlah>` mengembalikan `changes` berurutan menaik, `next_cursor`, dan `has_more`. Klien menerapkan setiap halaman dan melanjutkan selama `has_more=true`. Tombstone ikut dikirim untuk menyembunyikan baris yang dihapus di klien. `change_seq` dibuat di server dan memberi urutan yang stabil walaupun jam perangkat berbeda, meleset, atau memiliki waktu pengukuran yang sama.

## 3. (P3.3) Bukti implementasi

Jalur ulang praktikum dimulai dari `p3-sync`. Siapkan `deploy/.env` dari `deploy/.env.example` dengan kredensial lokal. Jalankan perintah berikut dengan port host 8000 dan 5432 tersedia. Proyek Compose tersendiri membuat volume P3 terpisah dari P2 sehingga inisialisasi skema P3 dapat berjalan.

```bash
docker compose -p musiwatch-p3 --env-file deploy/.env -f deploy/docker-compose.yml up -d --build
bash scripts/test_sync.sh
(cd android && bash ./gradlew :app:assembleDebug :app:lintDebug)
```

Uji ulang berjalan dengan Podman, PostgreSQL 16, dan emulator Pixel 10 API 36. Build debug dan lint Android lulus. Kontainer API merespons SIGTERM dalam 316 ms dengan exit code 0.

### Potongan kode DAO

`applyPushResults` memperbarui status dan versi berdasarkan keputusan server.

```kotlin
for (r in results) when (r.status) {
    "created", "updated", "duplicate" -> setSyncState(r.id, "SYNCED", r.version)
    "conflict" -> setSyncState(r.id, "CONFLICT", byId(r.id)?.version)
}
```

`upsertFromServer` menyimpan perubahan server sambil mempertahankan baris lokal yang masih dikerjakan atau berkonflik. Seluruh metode ada di [MeasurementDao.kt](../android/app/src/main/java/id/unsri/musiwatch/data/MeasurementDao.kt).

```kotlin
for (c in changes) {
    val local = byId(c.id)
    if (local != null && local.syncState != "SYNCED") continue
    upsert(c.toEntity())
}
```

## 4. Refleksi

Aplikasi menampilkan `CONFLICT` di samping nilai lokal dan menjelaskan bahwa server telah berubah. Untuk menyelesaikan konflik, layar lanjutan sebaiknya memperlihatkan nilai lokal dan nilai server beserta versinya. Petugas dapat menerima versi server atau mengirim koreksi baru dengan versi server sebagai `base_version` setelah meninjau perbedaan. Riwayat keputusan membantu penelusuran koreksi pengukuran.
