## 1. P3.1 – Analisis Kebutuhan Data dan Sinkronisasi

### A. Entitas dan sifat data

Entitas utama yang disinkronkan adalah `measurements` (pengukuran kualitas air). Setiap baris memiliki ID UUID yang dibuat oleh klien, ID stasiun, ID petugas, nilai pH, kekeruhan, suhu, catatan, waktu pengukuran, nomor versi, penanda penghapusan, dan nomor urut perubahan dari server.

Data pengukuran merupakan catatan yang perlu dipertahankan sebagai riwayat pengukuran. Namun, berdasarkan protokol pada praktik ini, baris pengukuran masih dapat diperbarui ketika koreksi dilakukan. Jadi, data ini tidak sepenuhnya append-only. Perubahan dikendalikan dengan `version` dan `base_version`. Penghapusan juga tidak dilakukan secara fisik, melainkan menggunakan tombstone (`deleted = true`).

Data yang dapat diedit bersama adalah baris pengukuran yang sama apabila beberapa perangkat memiliki salinannya. Kondisi ini dapat menimbulkan konflik jika dua perangkat mengubah baris yang sama berdasarkan versi yang sama.

### B. Potensi konflik dan konsistensi

Contoh konflik: perangkat A dan B sama-sama mengambil data versi 1. Perangkat A lebih dahulu mengirim perubahan dan server menaikkan versi menjadi 2. Ketika perangkat B mengirim perubahan dengan `base_version = 1`, server membandingkannya dengan versi 2 dan mengembalikan status `conflict`. Perubahan B tidak diterapkan sehingga data terbaru di server tidak tertimpa diam-diam.

Konsistensi dijaga melalui beberapa aturan:
- Setiap pengukuran mempunyai ID unik dari klien agar pengiriman ulang tidak membuat baris baru.
- `base_version` diperiksa sebelum pembaruan diterapkan.
- Data lokal yang masih `PENDING` atau `CONFLICT` tidak ditimpa oleh hasil pull.
- Penghapusan disebarkan sebagai tombstone agar perangkat lain mengetahui bahwa data telah dihapus.
- Perubahan server diambil secara bertahap menggunakan cursor `change_seq`.

### C. Risiko commit tidak berurutan dan mitigasi

Sequence PostgreSQL memberikan nomor ketika perubahan dibuat, bukan menjamin urutan commit transaksi. Misalnya transaksi pertama memperoleh `change_seq = 104`, tetapi belum commit. Transaksi kedua memperoleh 105 dan commit lebih dahulu. Jika klien menarik data sampai cursor 105, perubahan 104 yang baru commit kemudian dapat terlewat karena klien meminta perubahan setelah 105.

Pada implementasi praktik ini, mitigasinya adalah advisory transaction lock melalui `pg_advisory_xact_lock(42)`. Lock tersebut menserialisasi penulis sehingga transaksi yang memakai mekanisme ini tidak saling mendahului saat commit. Konsekuensinya, konkurensi penulisan berkurang. Untuk sistem produksi, alternatifnya adalah memakai log replikasi database atau menahan cursor di bawah transaksi tertua yang belum selesai.

## 2. P3.2 – Desain Data dan API Sinkronisasi

### A. Skema data lokal dan server

**Penyimpanan lokal Android (Room)** menggunakan tabel `measurements` dengan kolom berikut:

| Kolom | Fungsi |
|---|---|
| `id` | UUID pengukuran yang dibuat klien dan menjadi primary key |
| `stationId` | Identitas stasiun |
| `officerId` | Identitas petugas |
| `ph` | Nilai pH |
| `turbidityNtu` | Nilai kekeruhan |
| `tempC` | Suhu |
| `note` | Catatan |
| `measuredAt` | Waktu pengukuran dalam bentuk timestamp lokal |
| `version` | Versi server; null berarti belum pernah diterima server |
| `deleted` | Penanda tombstone |
| `syncState` | Status lokal: `PENDING`, `SYNCED`, atau `CONFLICT` |

**Penyimpanan server (PostgreSQL)** menggunakan tabel `measurements` dan sequence `change_seq_gen` pada `api/db/001_init.sql`.

| Kolom server | Fungsi |
|---|---|
| `id` | UUID primary key dari klien |
| `station_id`, `officer_id` | Identitas stasiun dan petugas |
| `ph`, `turbidity_ntu`, `temp_c` | Nilai pengukuran |
| `note` | Catatan pengukuran |
| `measured_at` | Waktu pengukuran bertipe `TIMESTAMPTZ` |
| `version` | Nomor versi data, default 1 |
| `deleted` | Penanda penghapusan/tombstone |
| `change_seq` | Nomor urut perubahan dari server |

Server juga memiliki indeks pada `change_seq` dan pada kombinasi stasiun serta waktu pengukuran untuk membantu pencarian data.

### B. Kontrak Push

Endpoint: `POST /v1/sync/push`

Perangkat mengirim batch perubahan dalam properti `changes`. Setiap item berisi `id`, `base_version`, identitas stasiun dan petugas, nilai pengukuran, waktu, serta penanda `deleted`.

Contoh request:

```json
{
  "changes": [
    {
      "id": "UUID-PENGUKURAN",
      "base_version": null,
      "station_id": "S-001",
      "officer_id": "u-118",
      "ph": 7.2,
      "turbidity_ntu": null,
      "temp_c": null,
      "note": null,
      "measured_at": "2026-11-10T08:00:00Z",
      "deleted": false
    }
  ]
}
```

Contoh bentuk response:

```json
{
  "results": [
    {
      "id": "UUID-PENGUKURAN",
      "status": "created",
      "version": 1
    }
  ]
}
```

Status per item:
- `created`: ID belum ada dan data baru berhasil dibuat.
- `duplicate`: ID sudah ada dan kiriman ulang tidak membuat data baru.
- `updated`: versi dasar cocok sehingga pembaruan diterapkan dan versi dinaikkan.
- `conflict`: versi dasar tidak cocok; server mengembalikan `server_version` dan tidak menerapkan perubahan tersebut.

Batch dibatasi maksimal 500 perubahan. Pemeriksaan versi dilakukan di server dalam transaksi database.

### C. Kontrak Pull

Endpoint: `GET /v1/sync/pull?since={cursor}`

Parameter `since` berisi cursor terakhir yang telah diproses perangkat. Server mengambil baris dengan `change_seq > since`, mengurutkannya berdasarkan `change_seq`, dan membatasi jumlah hasil maksimal 500 baris.

Bentuk response:

```json
{
  "changes": [
    {
      "id": "UUID-PENGUKURAN",
      "version": 2,
      "deleted": true,
      "change_seq": 105
    }
  ],
  "next_cursor": 105,
  "has_more": false
}
```

Perangkat menyimpan `next_cursor` dan mengulangi pull selama `has_more` bernilai true.

### D. Aturan konflik dan alasan menggunakan change_seq

Jika `base_version` sama dengan versi server, perubahan diterapkan dan versi dinaikkan. Jika tidak sama, server mengembalikan `conflict`. Pada Android, status lokal menjadi `CONFLICT`, sehingga data tersebut perlu ditinjau petugas dan tidak dianggap sudah tersinkron.

Cursor menggunakan `change_seq`, bukan timestamp perangkat, karena jam perangkat dapat berbeda atau tidak akurat. Nomor urut dari server memberikan penanda perubahan yang dikelola pada satu sumber. Risiko urutan commit yang tidak berurutan tetap perlu ditangani, pada praktik ini dengan advisory lock seperti dijelaskan di bagian P3.1.

## 3. P3.3 – Implementasi Backend, Android, dan Bukti

### A. Implementasi backend

Backend menggunakan FastAPI pada `api/app/sync.py` dengan router prefix `/v1/sync`. Endpoint `/push` menerima batch perubahan dan memeriksa ID serta versi. Endpoint `/pull` mengirim perubahan berdasarkan cursor. Database PostgreSQL didefinisikan melalui `api/db/001_init.sql`.

### B. Implementasi Android

Android menggunakan Room untuk menyimpan data secara lokal dan WorkManager untuk menjalankan sinkronisasi. Status data lokal adalah `PENDING`, `SYNCED`, atau `CONFLICT`. Worker mengirim data pending terlebih dahulu, kemudian mengambil perubahan dari server secara bertahap. Jika terjadi `IOException`, worker mengembalikan `Result.retry()` agar WorkManager menjadwalkan percobaan ulang.

### C. Potongan kode applyPushResults

Potongan berikut diambil dari `android/app/src/main/java/id/unsri/musiwatch/data/MeasurementDao.kt`:

```kotlin
@Transaction
open suspend fun applyPushResults(results: List<PushResult>) {
    for (r in results) when (r.status) {
        "created", "updated", "duplicate" ->
            setSyncState(r.id, "SYNCED", r.version)
        "conflict" ->
            setSyncState(r.id, "CONFLICT", byId(r.id)?.version)
    }
}
```

Fungsi ini mengubah status lokal menjadi `SYNCED` jika server menyatakan data berhasil dibuat, diperbarui, atau merupakan kiriman duplikat. Jika terjadi konflik, status menjadi `CONFLICT` dan versi lokal dipertahankan.

### D. Potongan kode upsertFromServer

Potongan berikut juga diambil dari `MeasurementDao.kt`:

```kotlin
@Transaction
open suspend fun upsertFromServer(changes: List<ServerChange>) {
    for (c in changes) {
        val local = byId(c.id)
        if (local != null && local.syncState != "SYNCED") continue
        upsert(c.toEntity())
    }
}
```

Fungsi ini menerapkan perubahan dari server ke Room. Jika data lokal masih berstatus selain `SYNCED`, perubahan server dilewati agar data lokal yang belum tersinkron atau sedang konflik tidak tertimpa.

### E. Pengujian protokol melalui scripts/test_sync.sh

Script `scripts/test_sync.sh` menguji enam tahap: data baru (`created`), kirim ulang (`duplicate`), pembaruan (`updated`), konflik (`conflict`), penghapusan sebagai tombstone (`updated` dengan `deleted = true`), dan pull.

**Urutan hasil yang diharapkan menurut skenario script** adalah:

| Tahap | Hasil yang diharapkan |
|---|---|
| Push data baru | `created`, versi 1 |
| Kirim ulang ID yang sama | `duplicate` |
| Ubah dengan base_version 1 | `updated`, versi 2 |
| Ubah lagi dengan base_version 1 | `conflict`, server_version 2 |
| Hapus dengan base_version 2 | `updated`, versi 3 dan `deleted = true` |
| Pull | Baris tombstone muncul dengan `change_seq` terbaru |

### G. Checkpoint mode pesawat (offline-first)

Checkpoint yang diminta modul dilakukan dengan urutan:
1. Jalankan API dan database MusiWatch.
2. Aktifkan mode pesawat pada emulator atau perangkat Android.
3. Simpan lima pengukuran dan pastikan tersimpan lokal dengan status `PENDING`.
4. Tutup aplikasi.
5. Matikan mode pesawat dan pastikan koneksi tersedia.
6. Tunggu WorkManager menjalankan sinkronisasi.
7. Pastikan kelima data diterima server, muncul pada hasil pull tanpa duplikat, dan status aplikasi berubah menjadi `SYNCED`.

**Status bukti saat dokumen ini diperbarui:** bukti checkpoint lima pengukuran dalam mode pesawat belum tercantum di daftar screenshot yang tersedia. Karena itu, keberhasilan checkpoint belum dinyatakan. Tambahkan screenshot saat lima data masih offline dan setelah seluruhnya tersinkron, atau log aktual dari emulator/perangkat.

## 4. Refleksi

Item berstatus `CONFLICT` sebaiknya ditampilkan dengan label atau ikon peringatan seperti “Perlu penyelesaian”. Saat item dibuka, aplikasi dapat menampilkan perbandingan nilai lokal dan nilai server, termasuk nilai pH, kekeruhan, suhu, catatan, waktu perubahan, dan versi data.

Petugas kemudian dapat memilih data yang benar atau menggabungkan informasi jika aturan aplikasi memungkinkan. Sebelum keputusan disimpan, aplikasi sebaiknya meminta konfirmasi. Data konflik tidak boleh langsung dihapus atau ditimpa karena dapat menyebabkan hilangnya hasil pengukuran.

## 5. Kesimpulan

Praktik 3 membangun mekanisme sinkronisasi offline-first melalui Room, WorkManager, FastAPI, dan PostgreSQL. Protokol menggunakan ID klien, nomor versi, status per item, tombstone, serta cursor `change_seq`. Pengujian protokol mencakup pembuatan data, pengiriman ulang, pembaruan, konflik, penghapusan, dan pull. Bukti checkpoint mode pesawat dengan lima pengukuran dan output eksekusi script perlu dilengkapi berdasarkan pengujian aktual sebelum laporan dinyatakan lengkap.
